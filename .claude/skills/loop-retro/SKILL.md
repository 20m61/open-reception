# loop-retro — 規約を実データから改善する（外側ループ）

`/loop-round` が**内側**ループ（1 Issue を 1 周する）なら、これは**外側**ループ
（規約そのものを 1 周する）である。内側は成果物を出し、外側は**内側の質を上げる**。

**あなたは今回の周回の当事者ではない。** 直前に自分が踏んだ失敗を、その場で規約へ
書き足すためのスキルではない。**複数の周回の実績を集めてから**書く。同じ周回で書くと、
`CLAUDE.md`「検証の作法」冒頭と同型の失敗になる —— 自分で導いた述語をそのままテストに
すると、テストとコードが同じ誤りを共有する。規約でも同じことが起きる。

## 出力

`.claude/rules/opus5-autonomous-loop.md` への **PR 1 本**。または
**「変更なし」**（これも正当な結果）。どちらの場合も `docs/loop-retro.md` に 1 行足す。

🔴 **規約を main へ直接 commit しない。** 人間のレビューを必ず通す。

## 手順

### 1. 現在地を読む

```sh
npm run loop:retro -- --report
```

規約版・教訓の在庫（帰属つき・古い順）・過去の実行記録・指摘が出る。**ここから始める**。
教訓を数えたり帰属を手で導いたりしない（そこで誤ると以降の判断が全部ずれる）。

### 2. 信号を集める

観測範囲は**前回の実行以降**（初回は直近 14 日）。集めるのは次の 4 つ。

| 信号 | どこから | 重み |
| --- | --- | --- |
| **人間の訂正** — ユーザーが方針を差し戻した / interrupt した | 周回のやりとり、PR レビュー | **ground truth** |
| **ゲートの FAIL** — 何が落ちたか、原因は退行か環境か | `docs/gate-runs.md`、`npm run evaluate:gate-runs -- --report` | 強 |
| **独立レビューの BLOCKER / MAJOR** — とくに**直前の自分の修正が作った**もの | `change-reviewer-opus5` の結果、PR のレビュー | 中 |
| **無風の周回** — 指摘なくマージされた | マージ済み PR | **弱い肯定**（規約が効いている証拠として数える） |

```sh
gh api "repos/{owner}/{repo}/pulls?state=closed&per_page=50&sort=updated&direction=desc"
```

🔴 **無風を 0 件と読まない。** 「指摘が出なかった」は「観測していない」ではなく
**弱い肯定**である。これを数えないと、規約は永久に増える方向にしか動かない。

### 3. 教訓へ一般化する

**採るのは、再発しうる類型と、その正しい扱いだけ。**

- ✅ 良い: 「早期 return が後段を飲み込む型の変異を、変異検証に必ず入れる」
- ❌ 悪い: 「#788 のボタンが隠れていた」（一発ネタ。二度と同じ形では起きない）
- ❌ 悪い: 「気をつける」「丁寧にやる」（検証できない）

**同じ類型を 2 周以上で観測できたものを優先する。** 1 件しか根拠が無いものは、
次回まで観測バックログに置く（`docs/loop-queue.md` へは書かない。キューが腐る）。

**まず fitness function にできないかを見る。** 規約へ書くのは最後の手段である。
`docs/ai-development-loop.md` §5 の一覧が示すとおり、このリポジトリは「規律で守るもの」を
機械検証へ移してきた。**散文へ足すのは、機械化できないと確かめてから。**

### 4. 規約を編集する

`.claude/rules/opus5-autonomous-loop.md` を編集する。

- 教訓は `> 由来: <YYYY-MM-DD> / #<issue>（PR #<n>）。<何が起きたか>` の引用ブロックで書く。
  **帰属が無い教訓は機械検証が落とす**（`missing_provenance`）。
  🔴 **素の bullet で書かない。** 上限も帰属検査も `> 由来:` ブロックしか数えないので、
  素の bullet で書いた教訓は**検査を丸ごと素通りする**。規約が黙って伸びる唯一の抜け道が
  ここなので、形式は守る（機械では塞げない。守るのはあなたの仕事）。
- 既存の教訓と**矛盾する**なら、新しい bullet を足すのではなく**古い方を改訂か削除**する。
  矛盾したまま並べると、次に読む者がどちらに従うか決められない。
- **上限 15 件**（`GUIDELINE_BUDGET`）。当たったら重なるものを統合するか、証拠の弱いものを
  剪定する。**剪定した理由も PR 本文に書く**（黙って消すと、なぜ消えたか誰も辿れない）。
- `<!-- loop-rules-revision: N -->` を **+1 する**。

#### ガード

- **停止境界と記法そのものを変えない。** §「停止境界」の列挙、Experience loop の順序、
  `> 由来:` の**記法**、版マーカーの**書式**は、このスキルからは変えない（変えるべきだと
  判断したら、PR 本文にその提案を書いて人間へ渡す）。
  🔴 **版マーカーの「数」を上げるのは手順 4 のとおり必ず行う。** 変えないのは書式であって
  値ではない。ここを取り違えて版を据え置くと、**この仕組みが存在する理由である帰属が
  測れなくなる**（レビューで実際にこの読み違いを指摘された）。
- **値の調整を繰り返さない。** 直前の周回の指摘に対して数値を動かすだけの変更が 2 回
  続いたら、前提そのものを疑う（本規約「レビューの停止条件」と同じ）。
- **信号が弱い・矛盾しているなら変更しない。** 「変更なし」で終わってよい。

### 5. 記録して PR を出す

`docs/loop-retro.md` に 1 行追記する（`NO_CHANGE` でも必ず）。

```sh
git checkout -b chore/loop-retro-$(date -u +%Y%m%d)
./scripts/quality-gate.sh --pr
```

PR 本文には**必ず**次を書く。

1. **観測した範囲**（期間 / PR 番号 / ゲート記録の行）と、無風だった周回の件数。
2. **信号ごとの根拠**（どの訂正・どの FAIL・どのレビュー指摘か。番号で引けること）。
3. **前回の教訓が効いたか。** 版 N で入れた教訓に対応する失敗が、版 N 以降に再発したか。
   **これが外側ループの本体である** —— 帰属を付けているのはこれを測るため。
   再発しているなら、教訓の文言ではなく**前提**が誤っている。
4. **追加・改訂・剪定した教訓の全文**と、その根拠。
5. 変更しなかった場合は**その理由**（「信号が弱い」「1 件しか根拠が無い」等）。

## いつ回すか

- **2〜3 週ごと**（`npm run loop:retro` が 21 日で `stale` を出す）。
- 同じ失敗を **3 回**踏んだと気づいたとき（規約が言っていないか、言っていても効いていない）。
- 内側ループの周回が 10 本ほど溜まったとき。

**内側ループの最中には回さない。** 作業ツリーを共有すると品質ゲートのスタンプが
mtime で落ちる（本規約「変異検証エージェントは作業ツリーを隔離する」）。別の周回として回す。
