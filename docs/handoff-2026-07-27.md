## 2. このセッションで確定した事実（再調査不要）

### ブラウザ e2e はこのコンテナで動く

**第 15 wave の申し送り「exit 144 でブロックされ実行不可」は誤りだった。** 真因は Playwright
1.61.1 が要求する chromium ビルド（1228）とプリインストール版（1194）の不一致で、
`executablePath` を渡せば動く。`playwright.config.ts` が `/opt/pw-browsers/chromium` を
自動検出するようにしたので、**追加の env 指定なしで `--e2e` が通る**。

この stale な記録が 5 周にわたって「UI 変更はブラウザ検証できない」という誤った前提を作り、
#422 の着手判断を歪めていた。**環境の制約を記録するときは、次の周回が再検証できる形
（再現コマンドと実際の失敗メッセージ）で残すこと。**

### e2e の project 構成は 3 段（前後で共有状態を挟む）

```
pristine-state（既定シード前提）→ chromium-ipad（本体）→ flow-mutation（破壊的）
```

- `pristine-state` = `kiosk-checkout-i18n` / `kiosk-vrt-a11y`。**在館者ゼロ・seed の担当者のみ**を
  前提にしており、他 spec が残した来訪者・担当者があると空状態の文言と画面の高さが変わって落ちる。
- `flow-mutation` = 既存（#248/#321）。フローや共有シングルトン設定を書き換える spec。

### VRT baseline の落とし穴（実際に踏んだ）

スナップショット名は既定で **project 名を含む**。project を分けただけで別名になり、
**レビュー済み baseline が孤立して、その場の描画が新 baseline として自動生成される**
（＝退行がそのまま「正」として焼き付く）。`snapshotPathTemplate` で `chromium-ipad` 名に
固定して回避した。**VRT を別 project へ移すときは baseline の解決先を必ず確認すること。**

### 端末一覧はページネーションされる

`/admin/devices` の行を e2e で掴むときは、**一意名で `device-filter-keyword` を絞ってから**。
フルスイートでは他 spec の作った端末に押し出されて 2 ページ目以降へ移る。

### 指紋が 2 種類ある（取り違え注意）

| 関数 | 含むもの | 用途 |
| --- | --- | --- |
| `computeConfigHash` | context（端末 ID）+ version + 内容 | `/api/configuration/effective` 応答の `configHash` |
| `computeSectionsHash` | **内容のみ** | 版のスナップショット指紋・版比較・端末が heartbeat で報告する値 |

端末ごとに変わる前者を「期待値」に使えないため、反映状況の突き合わせは後者で行う。

**設計上の要点**（作り直さないこと）:
- 端末実行はセッション束縛が権威。query の tenant/site/kiosk は**無視して記録**（拒否しない =
  可用性維持）。draft は端末へ配信しない。越境は 403。
- 端末束縛の解決は **fail-closed**（`device-binding.ts`）。既存の `kiosk-gate.ts` /
  `maintenance-gate.ts` は fail-open で、**同じ解決が 3 実装ある**（台帳 §5 に重複概念として登録済み）。
- 秘匿値・PII の混入は resolver が**実行時に検査して fail-closed で拒否**する
  （`payload-contract.ts`）。規約ではなく機構で担保しているので緩めないこと。
- プレビュー経路では **kioskId が当該拠点の端末か台帳で確認**する（純関数では担保できない義務。
  塞がないと他テナントの機能フラグ値が観測できる。実際に一度穴を開けて塞いだ）。

### B. #420 受付体験の版管理 — **オープン継続**

`src/domain/experience-version/` + `src/lib/experience-version/` +
`/api/admin/experience-versions`（+ `/deployments`）+ `/admin/experience-versions`。

**increment 1 の設計は途中で覆した。** 「版は構成の指紋だけを持つ」設計では、指紋が指す中身

`ExperienceConfigurationSnapshot` を導入し、**下書き保存時にセクション値ごと固定**、公開版は

**残作業**:
- 実検証チェッカ（asset URL / motion mapping / call route 到達性）。現在の検証は

- **端末側の報告送信**（heartbeat にパラメータを付ける）— **解禁済**。`useKioskConfiguration` の
  `meta.contentHash` を heartbeat に載せるだけ。それまで全端末は `pending` として出る
- ナビ配線（`navigation.ts` は #421 が扱う）
- デモ公開モデル（#363 `domain/demo-studio/publication.ts`）との統合。台帳 §5 のとおり
  **版モデルは `domain/experience-version/` へ一本化し、両方を恒久的に残さない**

**運用が変わる点（台帳 §9 B-06 に登録済み・要ユーザー確認）**: 版管理を有効化した拠点では
「保存＝反映」ではなくなる。**版を作るまでは発生しない**ため既存拠点への即時影響はなし。
版を作っていない拠点は従来どおり live 配信で挙動不変。
