# 変異検証の holdout（#1201）

**実装者が当てた変異が全部 kill でも、それは「実装者の想定では穴が無い」でしかない。**
実装者に見せずに作った変異（holdout）でも測り、両者の kill 率を分けて報告する。

この文書は**手順と記録の形**を決める。レビューの停止条件（`.claude/rules/opus5-autonomous-loop.md`
「レビューの停止条件」）は**変えない**。holdout の結果は PR 本文への報告であって、それだけで
merge を止める規則ではない。基準に組み込むかは owner が判断する（#1201）。

## なぜ要るか

`.claude/rules/opus5-autonomous-loop.md`「方式を替えたら、前の方式が守っていた変異を当て直す」は、
既にこう書いている:

> 一覧は「自分が思いついた変異」でしかない。族そのものの見落としは独立レビューでしか出てこないので、
> 行列が全部 kill でも「穴が無い」とは言えない

eval 設計の定石（claude.dev「Automating eval design and hillclimbing」）は、同じ問題を
**train / test の分割**で扱う。改善に使ったケース（train）でだけ点が上がり、確かめるだけの
ケース（test）が横ばいなら、それは過学習の兆候とみなす。変異検証に当てはめると、次のようになる。

| eval | 変異検証 |
| --- | --- |
| train（改善に使う） | 実装者が当て、生き残りを見てテストを足した変異 |
| test（確かめるだけ） | **実装者に見せずに**作った変異。生き残っても、それを見てテストを足すのは次の周 |
| train は上がり test は横ばい | 実装者の行列は全 kill なのに、holdout で生き残る → テストが実装者の想定に過学習している |

**実例（#1195 / PR #1199、2026-09-28）**:

- 実装者の行列は 33/33 kill（修正後は 39/39）だった。
- 独立レビューは、行列に無かった族を 1 周目に見つけた。自己テスト用の seam や `--full --no-build` で起動した実行でも、PASS と書けていた。
- 2 周目にも別の族が出た。検出器の差し替えと、e2e の向け先の差し替えである。
- どちらも「実装者が思いつかなかった面」であり、実装者の kill 率からは見えなかった。

**この手順を最初に当てた実測（#1200 / PR #1202、2026-09-28）**:

| | kill |
| --- | --- |
| train（実装者の行列） | 21/21 |
| holdout（独立レビュー。実装者の行列を見る前に diff から作成） | **29/39** |

- holdout の生存 10 件のうち 1 件は MAJOR だった。判定の優先順で最上位にある規則（train 側で劣化したら採用しない）を縛るテストが無く、その判定を消しても 97 本のテストが全部緑のままだった。
- 実装者の行列は、この規則の分岐を「両側で劣化するケース」でしか通していなかった。holdout 側の検査が先に効くので、train 側の検査を消しても落ちなかった。
- **train が全 kill でも holdout で生き残る**、という上の読み方の 2 行目がそのまま出た。

## 手順

### 実装者（train）

変異の行列を PR 本文に表で残す。**どこから導いたか**も書く（`.claude/rules/opus5-autonomous-loop.md`
「行列は変更した振る舞いの面を機械的に棚卸しして導く」）。

（記入例）

```markdown
### 変異検証（train）

行列の出どころ: <例: assess の if を全列挙 + ゲート配線（begin / finish の 3 出口）+ 数値パラメータ>

| # | ファイル | 対象 | 置換 | 結果 |
| --- | --- | --- | --- | --- |
| 1 | src/domain/x.ts | `if (a > b)` | `if (false)` | kill |
```

### 独立レビュー（holdout）

**前提**:

- holdout を作るレビューは**コードを実行できる agent**で行う（worktree を作ってテストを走らせる）。
  `change-reviewer-opus5` は `permissionMode: plan` で実行できないので、この用途には使わない。
- **実装者は、依頼文に自分の行列を書かない。** 依頼文に行列が入っていると、レビュー側はその枠の中で考え、
  分割の意味が無くなる。比較のための数字（例: 「実装者は 21/21」）を渡すなら、「作り終えてから読む」と明記する。

変異を当てる独立レビューでは、次の順を守る。

1. **PR 本文の変異の節を読む前に**、diff だけから自分の変異を作る。
   - 棚卸しの対象は、分岐・配線（どこから呼ばれるか）・データフロー・副作用・数値パラメータ・外部入力の形（出力形式、環境変数、色付き出力など）。
   - 先に実装者の行列を見ると、その枠の中でしか考えなくなる。
2. `git worktree` で隔離して当てる。
   - 復元はフルパスで行う。
   - 前後で `git status --porcelain` を確かめる（`.claude/rules/opus5-autonomous-loop.md`「変異検証エージェントは作業ツリーを隔離する」）。
3. 結果を次の形で報告する（数字は記入例）。

```markdown
### 変異検証（holdout・独立レビュー）

train（実装者）: 39/39 kill ／ holdout（レビュー）: 7/9 kill

| # | 対象 | 置換 | 結果 | 実装者の行列に在ったか |
| --- | --- | --- | --- | --- |
| 1 | gate_count_flaky の ANSI 除去 | 除去しない | **生存** | 無い |
```

4. holdout で生き残った変異は、**「テストの穴」として上の表に別に報告する**。それだけで
   BLOCKER / MAJOR / MINOR の指摘にはしない ―― 重大度に写すと、既存の停止条件（「BLOCKER / MAJOR が
   ゼロの周が 1 回出るまで」）を通じて事実上の新しい停止条件になるため（独立レビューの指摘）。
   生存を調べて**振る舞いそのものの欠陥**（誤った判定・誤った出力）を確かめた場合に限り、通常の指摘として
   出す。それは holdout が無くても出すべき指摘である。生存を重大度へ写すかは owner が決める（#1201）。

### 読み方

| train | holdout | 意味 |
| --- | --- | --- |
| 全 kill | 全 kill | 両者の想定の範囲では穴が見つからない（「穴が無い」ではない） |
| 全 kill | 生存あり | **テストが実装者の想定に過学習している**。生存した変異の族を、次の周で行列の棚卸しの対象へ足す |
| 生存あり | — | 実装者の行列自体に穴が残っている。この状態の holdout は、train の穴と混ざって読みにくい |

🔴 **holdout の生存を見てテストを足したら、その変異はもう holdout ではない。**
次の周の holdout は、また新しく作る。同じ変異で測り直して「holdout も全 kill」と書かない。

## しないこと

- holdout の kill 率を merge の停止条件にしない（基準の変更は owner の判断・#1201）
- 実装者が独立レビューの holdout を先に見てから行列を作らない（順序が逆になると分割の意味が無い）
- 「全 kill」を停止の根拠にしない（`.claude/rules/opus5-autonomous-loop.md` と同じ）
