### 🔴 19. 「大きな文字」アクセシビリティ支援モード（#321）が**何も拡大していない**

> **訂正（2026-09-02、PR #866 の自動レビュー指摘を検証した結果）**: 当初この項目は
> 「`var(--font-md)` が未定義なので**その 1 要素だけ**拡大に追随しない」（MAJOR）と書いていた。
> 指摘のとおり**根本原因を取り違えており**、実測したところ `--font-body` / `--font-lg` /
> `--font-xl` を使う**すべてのテキストが拡大していない**。BLOCKER へ引き上げる。

`globals.css:86-88` は `:root` で `--font-body: calc(1.25rem * var(--a11y-font-scale))` と定義し、
`:1695-1701` は `.screen[data-a11y-font-scale='1.3'|'1.6']` で `--a11y-font-scale` **だけ**を上書きする。
しかし CSS カスタムプロパティの `var()` は**宣言された要素の計算値時点で置換される**ので、
`:root` での `--font-body` の計算値は `calc(1.25rem * 1)` に固定され、そのまま子孫へ継承される。
子孫で `--a11y-font-scale` を変えても、**既に置換済みの派生トークンは再計算されない**。

`:79-84` のコメントはこれと逆のこと（「参照時に『その要素で有効な値』を都度解決するため…
子孫要素すべてへ波及する（テーマ切り替えと同じ仕組み）」）を書いているが、**成り立たない**。
色トークンは `var(--color-x)` を*参照側*で解決するので波及するが、`--font-*` は
*宣言側*で数値へ潰れている ―― 同じ「仕組み」ではない。

実測（`src/app/globals.css` を実ブラウザへ読み込み、`.screen[data-a11y-font-scale="1.6"]` と
既定の `.screen` を並べて `getComputedStyle` で比較）:

| 要素 | 1× | 1.6×（期待） | 1.6×（実測） |
| --- | --- | --- | --- |
| `.screen__title` | 54.924px | 拡大 | **54.924px** |
| `.screen__lead` | 33.432px | 拡大 | **33.432px** |
| `.btn` | 35px | 拡大 | **35px** |

`.screen` 上の `--a11y-font-scale` は正しく `1.6` になっているのに、同要素の `--font-body` は
`calc(1.25rem * 1)` のまま。**属性は付くが寸法は 1 ピクセルも動かない。**

なぜ気づかれなかったか: `tests/e2e/kiosk-a11y-modes.spec.ts` は `data-a11y-*` 属性の付与と axe と
フロー完走を検査するが、**計算値もスクリーンショットも見ていない**（課題 61 と同じ穴）。
属性ベースのテストは「効いたこと」ではなく「宣言したこと」しか固定できない。

修正方針（Wave 0）: `.screen[data-a11y-font-scale='…']` の各ブロックで
`--font-body` / `--font-lg` / `--font-xl` を**派生値ごと再宣言する**（`--a11y-font-scale` の
上書きだけでは足りない）。`[data-area='admin']` の再定義も同じ構造なので同時に確認する。

**付随して**（当初この項目が指していたもの）: `globals.css:1201` の
`.kiosk-quick-actions__more` は未定義の `var(--font-md)` を参照しており、invalid at
computed-value time で継承へ落ちる。上の根本原因を直しても**この 1 要素だけは別途直す必要がある**。
同じファイルの `:1491` に「`var(--font-sm)` のような未定義トークンを書くと無効値になり継承が効く。
実際に踏んだ」と書かれている。**2 度目である。**

既存 Epic（`#777` / `#778` / `#780` / `#782` / `#421` / `#422`）は置き換えず、外側に落ちた分だけ足す。

## 提案する 4 つのガード

トークン統制が守っているのは「値が食い違っていないこと」だけなので、以下を足す。

- **G1 存在しない CSS 変数を落とす** … `src/**` の `var(--x)` を集め、フォールバック無しで
  定義が無ければ落とす。**課題 20 の 2 箇所と課題 19 の付随分（`--font-md`）を今日検出でき、
  `globals.css:1491` が記録した `--font-sm` の再発も止まる。** parity テストの隣に置ける。
  ⚠️ ただし **G1 だけでは課題 19 の根本原因は捕まらない** ―― `--a11y-font-scale` も
  `--font-body` も「存在する」ので、静的な存在検査は素通りする。派生トークンが実際に
  再計算されるかは G1' でしか見えない
- **G1' 派生トークンが子孫での上書きに追随することを計算値で縛る** …
  `.screen[data-a11y-font-scale='1.6']` を実ブラウザで描画し、`--font-*` を使う代表要素の
  `getComputedStyle().fontSize` が 1× より大きいことを検査する。**課題 19 はまさに
  「宣言は正しいが計算値が動かない」型**で、静的検査でも属性検査でも見えず、
  計算値を読むか画像を撮るかしか手が無い
- **G2 コントラストを実測で縛る** … トークンの組（本文×面・インク×アクセント・境界×面）の比を
  計算し、境界 3:1 / 文字 4.5:1 を割ったら落とす。高コントラストモードの上書き後も同じ関数で測る
- **G3 テーマの通り道を実測で縛る** … `--brand-accent` に既定と全く違う色を入れて描画し、
  既定アクセントの色相が 1 画素も残らないことを確認する（課題 22 の 5 箇所は目視では気づけない）
- **G4 lint の範囲を `src/app` と CSS へ広げる** … 生色リテラル禁止は
  `eslint.config.mjs:66` で `src/components/**` に限定されており、ランディング・404・ログイン・
  global-error・enroll が漏れている（課題 25 の生 `#0f172a` 3 つはこの穴から入った）。
  `globals.css` 自体にも未移行の白 alpha が 4 つ残っている（`:1309,1542,1572,1591`）

## 決定事項（2026-09-02・ユーザー判断）

本書公開後にヒアリングし、以下を確定した。**ここに書かれた 6 件は判断済み**で、Wave の実行に
あたって改めて確認を取る必要はない（ただし対 1 は移行手順そのものの設計が別途要る。下記）。

### D1. `/staff` と `/demo` は日本語のまま（課題 40 / 41）

「操作するのは自社の従業員と国内の見込み客」と割り切る。**方針として `docs/i18n-tts-design.md`
へ明記する**（現在この 2 面は記載自体が無く、意図的な非対応なのか漏れなのか区別できない
状態にある。それを解消することが D1 の実質的な成果物）。

Wave 2 の実装範囲はこれで確定 —— **CSS の実装・`error.tsx`・e2e に集中**し、辞書は触らない。
あとから多言語化する余地は残る（辞書へキーを足すだけ）。

### D2. 管理コンソールのアクセシビリティは WCAG AA の最低線まで（課題 32）

運用者は自社の従業員なので、キオスクのような**支援モードの UI は持たせない**。担保するのは
「標準的な支援技術で使えること」:

- キーボード操作 —— CRUD の `<form>` 化と Enter 送信（課題 13）、モーダルの focus trap（課題 15）
- フォーカスの可視化
- 必須と検証エラーの `aria` 関連付け（課題 14）
- 罫線コントラスト 3:1（課題 24）

**含めない**: 文字拡大（1.3×/1.6×）と高コントラストのメニュー。よって `[data-area='admin']` の
`--font-*` 再定義は課題 19 の修正対象から外してよい（キオスク側だけ直せばよい）。

### D3. 波の順序は計画どおり 1 → 2

社外デモが直近に無いため、先に設計システムを 1 つにしてから `/staff`・`/demo` を作る。
**Wave 2 で書く CSS が最初から共有プリミティブに乗る**ので手戻りが最小になる。

### D4. 対 1 —— 部署 / 組織は **#373 の移行を完了させ 1 画面にする**（課題 34）

> ⚠️ **これは停止境界（永続スキーマの非互換変更）に該当する判断で、ユーザー承認を得た**。
> ただし承認されたのは**方向**であって、移行手順ではない。

調査で分かったこと: これは「重複」ではなく**段階移行の途中の姿**だった。`OrganizationUnit` は
`organization-unit` という別コレクションで、`src/lib/organization/organization-repository.ts` の
コメントが「既存 `Department`/`staff.departmentId` を無改変のまま段階移行する」と明記し、
来訪者ディレクトリは compat reader で旧新どちらも読める。

したがって Wave 3 は**画面の再編だけでなくデータ移行を含む**ことになる。着手前に要るもの:

- `Department` → `OrganizationUnit` の移行手順（既存レコード・`staff.departmentId` の扱い）
- 旧コードが新レコードを誤読しない保証と、ロールバック手順
- **ADR**（`docs/adr/README.md` の基準「覆すのに実装のやり直しが要る決定」に該当する）

### D5. 対 2 —— 認証方式 / 外部連携は 1 画面に統合する（課題 35）

API は別系統（`/api/admin/auth` 対 `/api/admin/integrations` + `/secrets`）で、**重複しているのは
表示だけ**だった —— `IntegrationsManager.tsx:111,119` の `h1` が「認証・外部連携」で、`:125` に
「ログイン方式」節を持つ。よってデータモデルに触れずに解消できる。3 対の中で唯一、
**低リスクで完全に消せる重複**。ナビを 1 行にし、ログイン方式の描画を `StatusBadge` に揃える。

### D6. 対 3 —— 旧「呼び出しルート」を削除し、名称を 1 つにする（課題 38）

これも仕様判断ではなく**終わっていない廃止作業**だった。旧 `CallRoute`(#88) は本番発信から
参照されず（発信は `executeRoutedCall` → `RoutingPolicy`/`ContactEndpoint`, #374）、
`callRouteId` は `normalize.ts:17` で既に `RETIRED_KEY`、`routing/compat.ts` は消費者ゼロ。

`/admin/call-routes` と `routing/compat.ts` を削除し、旧 URL は redirect。名称は「取次ルート」へ
統一する（画面見出しの「呼び出しルート（文章形式）」も揃える）。**設定しても実通話に効かない
画面が残っている方が危険**なので、これは Wave 3 を待たず **Wave 1 の後始末として先に出してよい**
（削除であり、IA 再編に依存しない）。
