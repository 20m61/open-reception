### 増分 3b の決着: QR 受付は「回答」ではなく「引き渡し」

待機の 5 入口を契約へ寄せるにあたり、`checkin` だけが `ConversationAnswer` に収まらなかった。
状態機械を進めず `CheckinFlow`（別シェル）へ切り替える操作だからで、`intent` に `'start'` を
与えるのは嘘になる。**嘘の intent を通すと「回答の intent は必ずその状態で許可された
アクション」という安全不変条件が意味を失う。**

採った形（#494）:

| 種類 | 契約 | 意味 |
| --- | --- | --- |
| `answers` | `ConversationAnswer`（`presetPurpose?` を追加） | このターンの問いへの答え。状態機械のイベントを起こす |
| `handoffs` | `ConversationHandoff`（`to: 'checkin'`） | 会話を別のターン空間へ渡す。状態機械は進めない |

**押したときに起こることが違うので、取得関数もハンドラも分けた**（`turnAnswersFor` /
`turnHandoffsFor`、`startWithEntry` / `handoffToShell`）。画面が取り違えられない。

用件の先取り（部署→面会 / 配送 / その他）は**別のアクションを作らず** `presetPurpose` で表す。
受付の進み方は同じ `start` で、先取りは添える情報だから。

**表示定義はターンごとに引く。** 待機の `delivery`（用件を先取りする入口）と用件選択の
`delivery`（用件そのもの）は同じ id で別物。id だけで引くと片方が他方に化ける。

## 3. 引き継ぎ事項

### A. 「消費者ゼロの契約」は静かに腐る（4/4 で乖離）

`ConversationTurnView` は #422 が提案する対話契約そのもので、実装もテストも在った。
**しかし誰も呼んでいなかったため、中身が実挙動から乖離していることに誰も気づかなかった。**

| 乖離 | 種類 |
| --- | --- |
| `inputModes` が実在しない音声入力を宣言 | 虚偽の主張（アクセシビリティ） |
| `escapeHatches` が `confirming` の dedup を持たない | 退行の予約 |
| `answers` の文言 3 件が相違 | i18n 退行の予約 |
| `answers` が `fallback` に**存在しない CTA** を返す | **構造的な乖離** |
| `message` の主指示 4 件が相違 | 見出し退行の予約 |

**対処**: 契約の既定を i18n 辞書・実挙動と突き合わせる**メタテスト**を置く。
テストが無い契約は「在る」だけで「正しい」ではない。

### B. 配線の前に契約を真にする

`conversationTurnFor` を画面へ配線する作業は、**契約が偽なら乖離をそのまま退行として表に出す**。
順序は必ず「契約を真にする（inc5-a）→ 配線する（inc5-b）」。

### B-1. 「テストの中にしか無い対応」も消費者ゼロと同じく腐る

契約の `messageKeyForState` と画面の見出しの対応は、#487 以降 `ui-contract.test.ts` の
`expected` テーブルにしか存在しなかった。**本番コードに経路が無いまま「一致している」ことだけ
を検証している状態**で、契約側の既定文言を直しても画面は別の i18n キーを引き続ける
（テストは通り、画面だけ古いまま）。

#490 でこの対応を `components/kiosk/conversation-turn.ts` へ出し、画面は
`messageKeyForState` 経由で見出しを解決するようにした。**突き合わせテストは乖離を
検出するが、乖離を起こせなくするのは本番経路の一本化だけ。**

### B-1-2. 契約を直しても、画面が自前で判断していれば何も届かない

#489 は契約の「通信断では代替導線を返さない」を直したが、`ResultView` は自前で
`shouldOfferAlternativeContact` を呼び続けていた。**契約の修正は誰にも届いていなかった。**

#492 で配線したところ、`reception-screens.tsx` から当該 import ごと消えた。**判断が消える
ことが一本化できた証拠**になる（消えないなら二重実装が残っている）。配線の増分では
「画面側から何が消えたか」を確認するとよい。

### B-2. screenState キーの契約は avatarState キーの表示側より表現力が高い

`guidance.ts` の `cue`（`data-cue` として実 DOM に出る）と契約の `gazeTarget` は「どこへ誘導
するか」を別語彙で二重に持つ。**`cue` は avatarState キーなので構造的に正しくできない**:
`'guiding'` が `selectingTarget`（選択肢あり）と `fallback`（CTA なし）の両方を覆うため、
どちらか一方でしか正しくなれない。

**同概念が二重に存在するとき、粗い側に契約を合わせない。** #489 は screenState キーの契約を
正とし、既知の非対称（`fallback` のみ）を明示するテストで固定した。

### B-3. 同じリテラルを 2 分岐に持つと片方だけ直してズレる

`失敗` と `未応答` が同じ「代替の連絡先へ」を別々のリテラルで返していた。**このセッションが
潰し続けてきた乖離と同じ形**なので、`ALT_CONTACT_ANSWER` へ一本化した（#489 セルフレビュー）。

### C. vitest の green は型の正しさを意味しない（3 回踏んだ）

vitest は esbuild でトランスパイルするだけで**型検査をしない**。

- ブランド型（`TenantId`/`SiteId`）に生文字列を渡した → vitest 16/16 green・`tsc` FAIL
- 辞書索引が `string | undefined` → vitest green・`tsc` FAIL
- `sed` の一括改名が無関係な同名箇所（checkin 側の関数）を巻き込んだ → 対象ファイルの
  vitest 79/79 green・`tsc` FAIL

**実装直後に `npm run typecheck` も回す。** `npm test` だけで「完成」と判断しない。
**`sed` の一括置換は特に危険**（スコープを持たないので同名の別関数へ波及する）。

### D. 対称信号への「DC オフセット」のような弱い根拠で慣行を外さない

`floatToPcm16` を一律 32767 倍にし、コメントで「非対称だと DC オフセットが乗る」と正当化して
いたが、対称信号に対して高々 1 LSB の話で根拠として弱かった。慣行（負側 32768 / 正側 32767）
がフルレンジを使う。**自分の実装を守るためにコメントを書かない。**

### E. 「配信対象を絞る」指定は空 = 全部ではなく空 = どこにも（fail-closed）

`demoUse.targetDeviceIds: []` は「どの端末にも配らない」。配信対象を絞る意図で作った版が
指定漏れで全端末へ出るのが最悪の事故で、空配列はまさにその指定漏れの形。

### F. 1Password の署名で毎周回止まる（未解決）

`op-ssh-sign` が `failed to fill whole buffer` を返してコミットできない事象が本日 6 回以上。
前景ではハング、背景では即失敗、時間をおくと通ることもある。**一貫した説明が付いていない。**

`op signin`（CLI）はこの実行環境では効かない（`promptError`）。恒久対策としては 1Password の
SSH エージェント設定（署名鍵の「使用時に確認」）の見直しが候補だが**未検証**。
現状は各周回の最後にユーザーがコミットを実行する運用で回している。
