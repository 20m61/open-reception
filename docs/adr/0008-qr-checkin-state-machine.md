# ADR 0008: QR 受付の状態機械を今は統合しない（並存のコストは「修正が伝播しないこと」）

- ステータス: 採用（統合の**見送り**。並存コストの実害を 1 件是正し、検出の足場を残す）
- 関連: issue #98（QR 受付）、#422（ExperienceShell）、#375（招待モデル）、#418（親 Epic）
- 関連ドキュメント: `docs/experience/state-mapping.md` §5 D、ADR 0006（`scanning` の位置づけ）
- 現物: `src/domain/checkin/state.ts`、`src/components/kiosk/CheckinFlow.tsx`、
  `src/app/api/kiosk/checkin/confirm/route.ts`

## 決定

**`CheckinState` と `ReceptionState` を今は統合しない。** ただし「統合するか否か」を先に
決めるのではなく、**並存のコストを実測してから**判断した。測った結果、コストは
「**片方に入れた修正がもう片方へ伝播しないこと**」だった。実害が 1 件見つかったので是正し、
同種の乖離を見つけやすくする足場を残す。

## 測ったこと: 2 つの状態機械は何が違うか

```
受付: idle → selectingPurpose → selectingTarget → inputVisitorInfo → confirming → calling
                                                            → connected / timeout / failed / fallback → completed
QR:   idle → selectingMethod → checkingCamera → scanning → resolving → confirming → calling → completed
                                                     ↘ 6 種のエラー状態 → USE_MANUAL / RETRY
```

重なっているのは **`confirming` → `calling`（発信前の確認ゲート）だけ**で、前段はまったく違う。
QR は目的も相手も来訪者情報も**予約から来る**ので、`selectingPurpose` / `selectingTarget` /
`inputVisitorInfo` に相当する局面が存在しない。逆に受付側には `checkingCamera` / `scanning` /
`resolving` と 6 種の予約エラー（期限切れ・使用済み・失効・読み取り不能・カメラ不可・通信）が無い。

**統合すると、片方でしか起きない局面を相手側の遷移表に持ち込むことになる。** 受付状態機械は
現在 12 状態で、QR 固有の 9 状態を足すと 21 状態になり、しかもその大半は互いに到達しない。
「1 本のタイムライン」に見えるのは体験設計の抽象であって、遷移表の要件ではない。

## 実測で見つかった実害: 修正が伝播していなかった

第 36 wave（#453）で通常受付について「**通信断とサーバ失敗を同じ文言で伝えない**」を直した。
**QR 受付には同じ修正が入っていなかった。**

`/api/kiosk/checkin/confirm` は次を返しうる。

| 応答 | 意味 |
| --- | --- |
| 403 | 端末セッション切れ（来訪者の操作では直らない） |
| 400 | 予約を受け付けられない（QR 側の問題） |
| 503 | 上流へ到達できない |
| その他 | サーバ側で完了できなかった |

`CheckinFlow` はこれを**すべて `CALL_FAILED` → `networkError`** へ潰し、来訪者には一律で
「**通信に失敗しました。通常受付でお進みいただけます。**」と出していた。

通信が生きているのに「通信に失敗しました」と言うのは、体験設計の原則「システム状態を
沈黙させない」を実質的に満たさない。来訪者は端末を疑って無意味に再試行する。

**第 36 wave とまったく同じ形の欠陥が、8 か月分の周回を挟んで反対側に残っていた。**
これが並存の本当のコストである。

## 是正

`src/domain/checkin/failure.ts` を足し、理由ごとに文言を出し分ける。**状態は増やさない**
（第 36 wave と同じ方針。区別のために状態を増やすと、逃げ道・再試行・通常受付への切替の
組み合わせが状態ごとに倍になる）。

あわせて `renderCheckin` を位置引数から props オブジェクトへ寄せた。第 28 wave (#445) で
`renderScreen` の位置引数が 29 個まで膨れた前例があるため、増える前に直す。

## なぜ「今は統合しない」で止めるか

統合の是非は**体験設計の判断**（J-OR-03 を同一タイムラインに載せるか）であり、
`.claude/rules/opus5-autonomous-loop.md` の停止境界「主要 Journey / state / fallback の意味を
変える仕様判断」に当たる。**ここで決めるべきではない。**

決められるのは「並存を続ける場合に何を払い続けるか」で、それは上記のとおり
**修正の伝播漏れ**である。ADR 0006 で「QR は加速手段であって等価要件ではない」と決めた以上、
QR 経路が受付経路と同じ豊かさを持つ必要は無い。したがって**統合しない選択は妥当**だが、
「伝播漏れを検出できないまま並存させる」のは妥当でない。

## follow-up（本 ADR のスコープ外）

1. **状態名 `networkError` が実態より狭い。** 通信以外の失敗も受けるようになった。改名は
   `CHECKIN_STATES` / `CHECKIN_ERROR_STATES` / i18n キー対応表 / テストへ波及するので別増分。
2. **QR 受付には「担当者が応答しない」が無い。** 受付側は `calling` で応答を待ち
   `timeout` / `connected` / `failed` を区別するが、QR は `/checkin/confirm` が 201 を返した
   時点で `completed` になる。J-OR-03 の設計（通知して終わり）としては整合するが、
   J-OR-05（担当者不在）は QR 経路では表現できない。**これは体験設計の判断**。
3. **`USE_FALLBACK`（代表窓口）が QR 経路に無い。** エラー状態からの逃げ道は
   `USE_MANUAL`（通常受付へ）と `RETRY` の 2 つで、受付側の「代表窓口へ繋ぐ」に相当する
   導線が無い。通常受付へ落ちれば到達できるので行き止まりではないが、経路は 1 段長い。

## 却下した代替案

**「統合して 1 本の状態機械にする」**: 上記のとおり停止境界。加えて到達しない状態が大半を
占める遷移表になり、`escapeHatchesFor` のような「状態ごとの逃げ道」判定が QR 固有状態の
分だけ複雑化する。得るものは「見た目の一本化」で、伝播漏れは統合しても別の形で残る
（前段の局面が違う以上、片方にしか無い修正は生まれ続ける）。

**「伝播漏れの検出をテストで機械化する」**: 検討したが**見送った**。2 つの状態機械は
局面が違うので、「同じ修正が両方に在ること」を機械的に定義できない（今回の文言出し分けも、
受付側は `failureReason`、QR 側は HTTP ステータス由来で、形が違う）。
無理に共通テストを作ると、意味の無い形式的一致を強制することになる。
**代わりに本 ADR の「実測で見つかった実害」節を残し、片方を直すときにもう片方を見る手掛かりにする。**
