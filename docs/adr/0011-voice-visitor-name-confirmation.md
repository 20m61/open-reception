## 文脈

ADR 0007 は、発信前の確認ゲートを音声が迂回できないことを、構造で保証した。保証の実体は次の 2 つである。

- `VoiceSessionHooks` が `onResolved` しか公開していないこと。
- `KioskFlow` の `handleVoiceResolved` が `SELECT_TARGET` しか dispatch しないこと。

`exposure-guard.test.ts` が、この 2 つを縛っている。

その結果、音声だけでは受付を完遂できない（ADR 0007 の差分 C'）。目的の選択、氏名の入力、発信の確認には、タッチとキーボードが要る。

#1077（Minimum-Turn）と #1057（No Typing）は、氏名を声で受け取る方向を求めている。#1086・#1088・#1090 はその設計と実装だが、独立レビュー（2026-10-27）で次の欠陥が指摘された。

- planner が、確信度の高い音声の氏名から `SUBMIT_VISITOR_INFO` を**確認なしで**作る。#1088 MAJOR-1 / #1090 MAJOR-2。
- 中間の画面を飛ばして `confirming` へ畳むので、**入力前のプライバシー通知（#314）を見ないまま、氏名を声で取られる**。#1088 MAJOR-1。
- 氏名と目的は、STT の確信度を見ていない。騒音で聞き違えた氏名が、`resolved/high` になる。#1090 MAJOR-2。
- 音声も有人支援も使えないとき、受付が行き止まりになる。今日のキーボードでの完遂の経路を失う。#1088 MAJOR-2。
- カスタム受付フローの必須の欄を迂回する。#1086 MAJOR-3 / #1088 MAJOR-1。

owner の判断（2026-10-28）: 音声で聞き取った氏名を確定できるようにする。あわせて、プライバシー通知の見せ方と、聞き違いへの対策を決める。

## 決定

### 1. 境界をどう広げるか

音声が受付状態機械へ起こせるイベントを、次の 2 つに広げる。

| イベント | 音声から起こせるか | 条件 |
| --- | --- | --- |
| `SELECT_TARGET` | 起こせる（ADR 0007 のとおり） | 高信頼でも、**同じ姓の担当者が 2 人以上いるときは必ず復唱する**（下の 3-f。#1284） |
| `SUBMIT_VISITOR_INFO` | **起こせる（新規）** | 下の 2〜4 をすべて満たしたときだけ |
| `SELECT_PURPOSE` | 起こせない（今回は広げない） | 別の ADR で扱う |
| `CONFIRM`（発信） | **起こせない（維持）** | 発信の直前の確認は、引き続きタッチの 1 か所だけ |

- 公開する面は、`VoiceSessionHooks` に `onVisitorNameConfirmed(name)` の 1 つを足すだけにする。
- `exposure-guard.test.ts` は、「公開するのは `onResolved` と `onVisitorNameConfirmed` だけ」に改め、dispatch は**ハンドラごとに**縛る（`onResolved` の処理 → `SELECT_TARGET` だけ、`onVisitorNameConfirmed` の処理 → `SUBMIT_VISITOR_INFO` だけ）。1 つの一覧へ足すだけにしない（新しいハンドラが検査の範囲から漏れるため）。
- 不変条件として、**音声のどの経路からも `CONFIRM` が起きない**ことを縛る。フォームの submit を経由する間接の dispatch も含める（カスタムフローで欄へ値を入れる経路は、`SUBMIT_VISITOR_INFO` までで止まる）。
- `REQUIRES_CONFIRMATION_ACTIONS` の `submitVisitorInfo` は外さない。音声の経路では、「明示の操作」を**復唱への肯定**と定義する（下の 3）。

### 2. プライバシー通知をどこで、どう見せるか

- **氏名を聞き取るのは、`inputVisitorInfo` の画面に居るときだけ**にする。ほかの画面（目的の選択・相手の選択・idle）の発話から氏名を抜き出しても、その場では使わない。氏名を先回りで埋めるために、`inputVisitorInfo` の画面を飛ばすことはしない（#1088 の `materializationActionsForDraft` を、`inputVisitorInfo` で止まる形に直す）。
- `inputVisitorInfo` に入ったら、まず `PrivacyNotice` の要約を画面に表示する（#314 の現行どおり、入力欄より上）。氏名を尋ねる前に、TTS で通知の短い版を読み上げる。例:「受付のため、お名前をお伺いします。声に出したくない場合は、画面から入力できます。記録の扱いは画面に表示しています」（構成は下の「固定の前置き＋要約」）。通知を**正常に**読み上げ終わったときだけ、氏名の聞き取りを始める。読み上げが失敗・中断したとき（アプリの `speak()` は `onerror` も終了の通知へ畳むので、終了と失敗を区別する）と、一定時間内に終了の通知が来ないとき（`speak()` は TTS が無効なときなどにコールバックを呼ばずに戻る。iPad Safari では終了の通知が来ないこともある）は、TTS が使えないときと同じ扱いにする（次の項）。
- **TTS が使えないとき（`ttsEnabled: false` など）は、音声での氏名の聞き取りを始めない。** 通知を読み上げられないまま氏名を声で取らないため。そのときはキーボードの欄だけを使う（下の 4）。
- 通知の文面の正本は、`resolvePrivacyNoticeContent` のまま変えない。読み上げる短い版は、同じ module に新しく置く（文面を二重に持たない）。
- 読み上げる文は「**固定の前置き**（氏名を伺うこと、声に出したくなければ画面から入力できること）＋要約」とする。要約は、テナントが上書きしている（`overrideSummary`）ときはその上書きを、していなければ新しく置く短い版を使う。前置きは上書きの有無に関係なく必ず読む（上書きの文面に、画面から入力できる旨が入っているとは限らないため）。
- 通知の要約は、タッチの経路と同じものを見せる（音声だけ別の文面にしない）。
- 公共空間で氏名を声に出させることへの配慮として、次を入れる。
  - 通知の中で、「声に出したくない場合は、画面から入力できる」ことを示す。
  - キーボードの入力欄は、常に同じ画面に置く（下の 4）。

### 3. 聞き違いへの対策

**a. STT の確信度の下限**
- 氏名の候補として扱うのは、STT の確信度が `minSttConfidence`（既定 0.6。`DEFAULT_ENTITY_RESOLUTION_THRESHOLDS`）以上で、**かつ**抽出器の確信度が `minProposalConfidence`（#1090 の `DEFAULT_SLOT_PROPOSAL_RESOLUTION_POLICY`。現在 0.72）以上のときだけにする。どちらの値も定数を参照し、ADR に数値を写さない。
- 下限を下回ったら、候補として画面に出さずに、もう一度尋ねる。
- 目的（purpose）を音声から扱うようになったときも、同じ下限を課す（#1090 MAJOR-2）。

**b. 氏名は、確信度に関係なく必ず復唱して確かめる（自動確定しない）**
- 相手（`SELECT_TARGET`）は、高信頼なら自動で採用しうる。一方、氏名は来訪者本人の個人情報で、聞き違えたまま担当者へ伝わると取り返しにくい。そのため、高信頼でも自動では確定しない。
- 復唱は、画面の表示と読み上げの両方で行う。例:「〇〇様でよろしいですか」。
- 来訪者の答えは、次のどちらでもよい（音声とタッチの等価）。
  - 声で「はい」「いいえ」と答える。
  - 画面のボタンを押す。
- 「はい」のときだけ、`onVisitorNameConfirmed` を呼ぶ。
- 声の「はい」「いいえ」にも、同じ STT の下限を課す。下限を下回った答えは「はい」とみなさず、答えなかったものとして扱う（下の c で 1 回と数える）。発信の直前の確認（`ConfirmView`）は、最後の安全弁として残る。

**c. 言い直しの上限（最初の質問 + 言い直し 2 回 = 計 3 回まで）**
- 次のどれかが起きたら、それを 1 回の失敗と数え、もう一度尋ねる（言い直し）。
  - 復唱に「いいえ」と答えた。
  - STT の確信度、または抽出器の確信度が下限を下回った（復唱への答えを含む）。
  - 氏名が長さの上限（下の e）を超えた。
  - 発話から氏名を抽出できなかった。
  - 一定時間、答えが無かった（時間の値は、実装する PR で定数として 1 か所に置く）。
- 言い直しは **2 回まで**とする。最初の質問と合わせて 3 回とも失敗したら、音声での氏名の聞き取りをやめる。キーボードの入力欄へフォーカスを移し、「画面から入力してください」と案内する。有人支援（#1074）が使えるときは、その導線も示す。
- 復唱への答えが失敗したとき（無応答・下限未満）は、「はい／いいえ」だけを聞き直さず、**氏名から聞き直す**（復唱の対象そのものが誤っている可能性があるため）。
- 回数は `inputVisitorInfo` に居るあいだの累計で数え、その画面を出たら（戻る・確認へ進む・リセット）数え直す。
- **確認画面から戻ったとき（氏名がすでに入っているとき）は、通知の読み上げも音声での聞き取りも自動で始めない。** 戻るのは任意の欄を入れるか氏名を直すためで、そこで氏名を尋ね直すと、打ち始める前の発話で氏名が上書きされうるため。直すのはキーボードで行う。
- キーボードへ移った後は、同じ画面の中では音声での聞き取りを自動で再開しない（キーボードでの入力を邪魔しない）。
- **来訪者がいずれかの欄へキーボードで入力し始めたら、その時点で音声の聞き取りと復唱を止める**（キーボードへ移ったものとして扱う）。音声で確定した氏名が、打ちかけの値や入力済みの任意の欄を上書きしたり、黙って捨てたりしないため。

**d. 発信前の確認**
- `confirming` の画面（`ConfirmView`）には、引き続き氏名を表示する。
- 戻る操作で `inputVisitorInfo` へ戻り、キーボードで直せる。
- 音声で確定した氏名も、タッチで入力した氏名と同じ確認を通る。

**e. 氏名の長さの上限**
- 氏名の長さの上限は、**今はどこにも無い**（`VisitorInfoView` にも `VisitorInfoForm` にも `maxLength` は無く、サーバ側の検証も無い）。
- 上限を新しく設ける。値は 1 つの定数として正本を 1 か所に置き、**音声とキーボードの両方に同じ値を課す**（音声だけ別の上限にしない）。値は、実装する PR（#1088 / #1090）で決め、owner の確認を経る。
- 上限を超えた発話は、氏名の候補にしない（上の c で 1 回と数える。#1090 MINOR-4）。

**f. 同じ姓の担当者が 2 人以上いるときは、相手も必ず復唱する（owner の決定、2026-10-28）**
- 相手（`SELECT_TARGET`）は、高信頼なら自動で採用しうる（上の 1）。ただし、在席・不在のどちらかの辞書に**同じ姓の担当者が 2 人以上**いるときは、完全一致の人が 1 人だけでも自動で確定しない。必ず復唱するか、来訪者に選んでもらう。
- 表示名が姓だけの人（「田中」）がいる場合も同じにする。確信度の差（完全一致と前方一致）を理由に、自動で確定しない。
- 不在の人を名指しされたときも同じで、同じ姓の別人がいれば「不在です」と断定せず、復唱して確かめる。
- **読みを登録していない担当者が 1 人でもいる名簿では、担当者を自動で確定せず（不在の断定もせず）、常に復唱する**（owner の決定、2026-10-28）。在席・不在のどちらの辞書でも、有効な担当者で読みが無い人が 1 人いれば当てはまる。文字を含まない読み（空白・「・」・「-」・長音符「ー」・「（えいぎょう）」のような注記だけ）も、読みが無いものとして扱う（CSV で空欄の代わりに「-」を入れる運用があるため）。読みの無い人とは、文字の系統の違い・同音異字・表に無い異体字を比べられないため。部署は姓を持たないので対象外。読みの登録を必須にするか促すかは #1287 で決める。
- 判定の正本は `kiosk-bridge.ts` の `sharesSurname`（#1285。**#1285 を先に merge する**）。辞書は姓と名を別の欄で持たないので、表示名と読み（kana）から推定する。要点は次のとおり。
  - 比較の前に、検索と同じ正規化（NFKC・小文字・カタカナ→ひらがな）をかけ、姓に多い異体字（邊・邉→辺、髙→高、﨑→崎、斎・齋→斉 など）を標準の字へ寄せる（来訪者の発話の STT は標準の字を出すため）。異体字セレクタ（IVS）は取り除く。括弧の注記（「田中（営業） 花子」「【営業】田中 花子」。丸・角・【】・〔〕・「」）は除く。空白（全角を含む）・読点・カンマ・中黒を区切りとして扱う。
  - 両方がラテン文字（アクセント記号つきを含む）なら、語順が違いうるので、どれか 1 語が共通なら同じ姓とみなす（「Smith」と「John Smith」、「García」と「José García」）。共通の名や前置詞（van・de）でも同じ姓とみなすが、増えるのは復唱だけ。
  - 両方が区切られていれば、先頭の語どうしを比べる。
  - 片方だけが区切られていれば、その先頭の語で、もう片方が始まるかを見る。1 文字の姓（林・森・東）も拾う。
  - どちらも区切られていなければ、先頭 2 文字以上が一致するときに同じ姓とみなす。
  - 表示名で決まらなければ、読みでも同じ判定をする。読みが登録されていない側は、かな・ラテン文字だけの表示名を読みとして使う。
  - **姓の長さが分からないときは、表示名の先頭 1 文字で判定する（安全側。owner の決定、2026-10-28）。** 表示名にも読みにも区切りが無いとき（読みが揃わず表示名に区切りが無いときを含む）は、表示名の先頭 1 文字が同じなら同じ姓とみなす（「林太郎」と「林花子」、「井太郎／いたろう」と「井花子／いはなこ」、同じ字で読みの違う「東」）。「佐藤／さとう」と「佐野／さの」のような別の姓どうしも同じ姓とみなし、復唱が増える。その費用（独立レビューの実測。区切り無し＋読みの 30 人の名簿で、自動確定しない人が 10/30 → 11/30）は owner が了承した。読みが両方にあり、表示名か読みのどちらかに区切りがあれば、それで姓が分かるので、この規則は使わない（読みが片方にしか無いときは表示名の区切りだけを見る。ただし、その名簿では上の決定で常に復唱になる）。
  - 文字の系統が違って比べられない組（かなの読みとラテン文字の読み。`sharesSurname` の単体の仕様としては、読みの無い「田中次郎」と「タナカ ジロウ」も含む）は、同じ姓とみなさない。みなすと、ラテン文字・かなの名前の人が 1 人いるだけで、辞書の全員の自動確定が止まる（実測: 30 人の辞書に 1 人足すと 31/31）。
  - 無効（disabled）の担当者は比較に入れない（解決の対象と揃える）。
- 安全側に倒すので、「佐藤」と「佐野」のように、姓の違う人どうしでも復唱が増えることがある。増えるのは復唱だけで、誤接続は増えない。読みを空白で区切って登録すれば区別できることが多い（読みの先頭 2 文字が一致する組（「たかだ」と「たかはし」）で、読みにも区切りが無いもの（姓だけの名前を含む）は引き続き復唱する）。
- 🔴 **了承した例外（owner の決定、2026-10-28）。** 上の 2 つの規則のあとも、全員に読みがある名簿で、次の組は同じ姓でも自動で確定しうる。
  - 異体字の表に無い字で、読みでも決まらない組（表は網羅ではない。読みが両方にあれば、多くは読みで拾う。例: 表に無い「邨」の「邨 花子／むらはなこ」と「村 太郎／むらたろう」は拾う）。
  - 文字の系統が違う同じ姓で、読みの文字の系統も違う組（「鈴木 一郎／すずき いちろう」と、読みをラテン文字で登録した「Taro Suzuki／taro suzuki」）。読みを、姓を先にしたかなで登録すれば拾う。同じ姓とみなす規則にすると、ラテン文字・かなの名前の人が 1 人いるだけで全員の自動確定が止まる（実測: 30 人の辞書に 1 人足すと 31/31）ので採らない。
- 読みの無い担当者がいる名簿では、上の決定で常に復唱になるので、読みの無い同音異字（「伊藤 太郎」と「伊東 花子」）や除けない注記（『』〈〉《》、閉じていない括弧）による取りこぼしは起きない。
- 拾えない型が運用で見つかったら、判定を足す。この節の説明と `sharesSurname` がずれたら、実装を正本とし、この節を直す（テストの正解表をこの節から起こさない）。

### 4. キーボードだけでも、受付を最後まで済ませられる経路を残す

- `inputVisitorInfo` のキーボード入力欄は、音声が使えるかどうかに関係なく、**常に表示して使える**ようにしておく。対象は、既定の受付経路の `VisitorInfoView`（`reception-screens.tsx`）と、カスタムフローの `VisitorInfoForm`（`custom-flow/VisitorInfoForm.tsx`）の**両方**。音声は、この画面の上に**足す**入力手段であって、置き換えではない。
- マイクの権限の拒否、STT の障害、`sttEnabled: false`（既定）、騒音、の**どの場合でも**、キーボードだけで `SUBMIT_VISITOR_INFO` → `CONFIRM` まで進める。
- ConversationDraft の planner（#1088）は、音声も有人支援も使えないときに `blocked` を返さない。キーボードでの入力（`collect`）を返す（#1088 MAJOR-2）。
- #1057（自由入力の排除）でキーボードを外すのは、**有人支援（#1074）が本番に配線され、owner が別途承認してから**とする。それまでは、この ADR の「キーボードを残す」が優先する。

### 5. カスタム受付フローとの関係

- 音声で埋めるのは `name` だけにする。カスタムフロー（#100）が定める必須の欄（`text`/`textarea`/`select`/`checkbox`）は、画面で埋める。
- `onVisitorNameConfirmed` を受けたら、`KioskFlow` は氏名を入力欄に入れる。そのうえで、**必須の欄がすべて埋まっているときだけ** `SUBMIT_VISITOR_INFO` を dispatch する。まだ必須の欄が残っていれば、`inputVisitorInfo` に留まり、その欄の入力を案内する。
- 目的の選択に応じて選ばれたカスタムフロー（`selectedFlow`）は、音声の経路でも変えない（今回、目的は音声から扱わない）。
- カスタムフローに `name` の欄が無い場合や、`visitorInfo` の step が無い場合は、氏名を聞き取らない。
- `VisitorInfoForm` は、今は初期値を受け取れず、値を内部の state に持つ。音声で確定した氏名を欄に入れるには、初期値（または外からの値）を受け取れるように改修する。
- 既定の受付経路では、必須の欄は氏名だけ。音声で氏名が確定したら、任意の欄（会社名・メモ）は空のまま `SUBMIT_VISITOR_INFO` へ進んでよい。任意の欄を入れたい来訪者は、確認画面から戻って入力できる。
- 会社名などの任意の欄は、音声から埋めない（#1090 の company の slot は、確定へ使わない）。

### 6. 個人情報の扱い

- 音声で取った氏名は、キーボードで入力した氏名と同じ扱いにする。
  - 監査ログ・experience metrics・アプリログに出さない（`.claude/rules/pii-secret-minimization.md`）。
  - 計測には、件数・回数・経過時間だけを使う。
- 途中の認識結果（interim）は、氏名の欄にも記録にも残さない。復唱に出すのは、確定した 1 つの候補だけにする。
- `RESET`、無操作でのリセット（#125）、キャンセル、受付の完了のときは、ConversationDraft と聞き取りの途中の状態を**必ず捨てる**。前の来訪者の氏名が、次の来訪者の画面に出ないようにする（#1088 の残存リスク）。
- 音声の生データは、保存しない。STT のために端末の外へ送る場合（ADR 0001 の WSS の経路）も、送った先で保存しない。氏名を含む派生データ（認識結果の全文など）も残さない。
- **氏名を含む発話（復唱など）は、動的な TTS キャッシュ（ADR 0002 の S3・CDN、および端末側の Service Worker / IndexedDB の層）に書かない。** 合成は端末の中（ブラウザの TTS）で行うか、サーバで合成するならキャッシュしない。保存期間の定めのない場所に、来訪者の氏名を残さないため。

## 代替案

1. **ADR 0007 のまま（音声で氏名を扱わない）**
   - 安全側は最も強い。ただし、#1077 と #1057 の目的（氏名をタイプさせない）に届かない。owner の判断で採らない。
2. **高信頼なら復唱せずに氏名を確定する（#1088 / #1090 の現行の実装）**
   - 来訪者の手数は最小になる。一方で、聞き違えた氏名が確認を経ずに入る。
   - さらに、中間の画面を飛ばすので、プライバシー通知を見ないまま氏名を取られる。
   - 取り返しにくい個人情報の確定には重すぎる危険なので、採らない。
3. **氏名の確定に加えて、`CONFIRM`（発信）も音声に開ける**
   - 「人を呼ぶ」という取り返しのつかない操作の手前の安全弁が、音声の認識と同じ経路に乗る。
   - ADR 0007 の「統合すると安全弁が弱まる」と同じ理由で、採らない。
4. **キーボードを先に外し、STT が使えないときは有人支援だけにする**
   - 有人支援（#1074）がまだ配線されていない。今キーボードを外すと、受付が行き止まりになる。採らない（上の 4）。

## 影響

### 実装（この ADR が承認されてから）
- **#1088**:
  - planner を `inputVisitorInfo` で止める。氏名は prefill の値として返す。
  - 音声も有人支援も使えないときは、`collect`（キーボード）を返す。
  - 無効な値が後から来た有効な値を阻まないように、`mergeSlot` を直す。
- **#1090**:
  - 氏名と目的に、STT の確信度の下限を課す。company の slot は、確定に使わない。
  - 同じ姓の不在の人による誤接続を直し（#1284 と同じ型）、それを正解として縛っているテストを直す。
- **#1086**:
  - 文書を、この ADR に合わせる。対象は、ui-contract との食い違い、カスタムフロー、失敗時の導線、PII 表示の制約。
- **`KioskFlow` / `kiosk-binding`**:
  - `onVisitorNameConfirmed` を足す。復唱の UI と、言い直しの上限を入れる。
  - 通知を読み上げ終えてから聞き取りを始める。
  - `exposure-guard.test.ts` を、上の 1 のとおりに改める。

### 運用・コスト
- 新しい外部送信や依存は無い（STT は既存の経路）。
- 受付 1 件あたりの読み上げ（通知と復唱）が増えるので、所要時間が数秒延びる見込み。受付の完遂率と所要時間の計測で確かめる。

### 撤回の条件
次のどれかが起きたら、音声での氏名の確定を止め（`onVisitorNameConfirmed` を配線から外す）、ADR 0007 の境界へ戻す。
- 聞き違えた氏名が担当者へ伝わった事例が、運用で確認された。
- 復唱の往復で、受付の完遂率が下がった。

撤回しても、キーボードの経路が常に残っているので、受付は止まらない。

## owner の決定（2026-10-28）

- 提案のとおり承認する。
- 言い直しの上限は「2 回」とする。
- 通知の読み上げは、毎回の受付で行う（省略の設定を設けない）。
- 来訪の目的（`SELECT_PURPOSE`）は、音声で聞き取る対象に入れない（この ADR の範囲外）。
- 同じ姓の担当者が 2 人以上いるときは、相手も必ず復唱する（上の 3-f）。姓は表示名と読みから推定するので、すり抜けを次のように扱う（2026-10-28 追加）。
  - 読みを登録していない担当者が 1 人でもいる名簿では、担当者を自動で確定せず、常に復唱する。
  - 表示名にも読みにも区切りが無いときは、表示名の先頭 1 文字で姓を判定する（自動確定しない人が 30 人の名簿で 10 人から 11 人に増えることは了承する）。
  - それでも残る例外（全員に読みがある名簿での、異体字の表に無い字と、文字の系統が違う同じ姓）は了承する（3-f）。
  - 管理画面で担当者の読み（姓と名を空白で区切る）の登録を必須にするか強く促すかは、#1287 の draft PR で案を見て決める。
