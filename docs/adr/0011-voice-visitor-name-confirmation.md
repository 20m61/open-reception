# ADR 0011: 音声で聞き取った来訪者の氏名を、確認を経て確定できるようにする（ADR 0007 の一部を置き換える）

- ステータス: **承認**（owner の判断、2026-10-28。下の「owner の決定」を含む。この ADR に依存する実装は、ADR の merge 後に行う）
- 置き換える範囲: [ADR 0007](0007-voice-touch-confirmation-boundary.md) の「音声が受付状態機械へ起こせるイベントは
  `SELECT_TARGET` だけ」という境界のうち、**来訪者の氏名の確定（`SUBMIT_VISITOR_INFO`）** に関する部分だけ。
  「`ReceptionState.confirming` と `VoiceKioskMode.readback` を統合しない」という ADR 0007 の決定は維持する。
- 関連: #1057（来訪者向け UI から自由入力を排除する方向）、#1074（入力途中の有人支援）、#1077（Minimum-Turn）、
  #1079 / #1081（ConversationDraft・slot の解決）、#314（入力前のプライバシー通知）、#370（STT と Entity の確信度）、
  #100（カスタム受付フロー）、#1284（誤接続）
- 関連 PR: #1086（文書）、#1088（ConversationDraft planner）、#1090（slot proposal）
- 現物: `src/lib/voice-session/kiosk-binding.ts`（`VoiceSessionHooks`）、`src/lib/voice-session/exposure-guard.test.ts`、
  `src/domain/reception/ui-contract.ts`（`REQUIRES_CONFIRMATION_ACTIONS`）、`src/domain/reception/state.ts`、
  `src/components/kiosk/reception-screens.tsx`（`VisitorInfoForm`・`PrivacyNotice`・`ConfirmView`）、
  `src/domain/voice-stt/entity-resolver.ts`（`DEFAULT_ENTITY_RESOLUTION_THRESHOLDS`）

## 文脈

ADR 0007 は、発信前の確認ゲートを音声が迂回できないことを、構造で保証した。保証の実体は次の 2 つである。

- `VoiceSessionHooks` が `onResolved` しか公開していないこと。
- `KioskFlow` の `handleVoiceResolved` が `SELECT_TARGET` しか dispatch しないこと。

`exposure-guard.test.ts` が、この 2 つを縛っている。

その結果、音声だけでは受付を完遂できない（ADR 0007 の差分 C'）。目的の選択、氏名の入力、発信の確認には、タッチとキーボードが要る。

#1077（Minimum-Turn）と #1057（No Typing）は、氏名を声で受け取る方向を求めている。#1086・#1088・#1090 はその設計と実装だが、独立レビュー（2026-10-27）で次の欠陥が指摘された。

- planner が、確信度の高い音声の氏名から `SUBMIT_VISITOR_INFO` を**確認なしで**作る。#1088 MAJOR-1 / #1090 MAJOR-2。
- 中間の画面を飛ばして `confirming` へ畳むので、**入力前のプライバシー通知（#314）を見ないまま、氏名を声で取られる**。#1088 MAJOR-1。
- 氏名と目的は、STT の確信度を見ていない。騒音で聞き違えた氏名が、`resolved/high` になる。#1090 MAJOR-2。
- 音声も有人支援も使えないとき、受付が行き止まりになる。今日のキーボードでの完遂の経路を失う。#1088 MAJOR-2。
- カスタム受付フローの必須の欄を迂回する。#1086 MAJOR-3 / #1088 MAJOR-1。

owner の判断（2026-10-28）: 音声で聞き取った氏名を確定できるようにする。あわせて、プライバシー通知の見せ方と、聞き違いへの対策を決める。

## 決定

### 1. 境界をどう広げるか

音声が受付状態機械へ起こせるイベントを、次の 2 つに広げる。

| イベント | 音声から起こせるか | 条件 |
| --- | --- | --- |
| `SELECT_TARGET` | 起こせる（ADR 0007 のとおり） | 高信頼でも、**同じ姓の担当者が 2 人以上いるときは必ず復唱する**（下の 3-f。#1284） |
| `SUBMIT_VISITOR_INFO` | **起こせる（新規）** | 下の 2〜4 をすべて満たしたときだけ |
| `SELECT_PURPOSE` | 起こせない（今回は広げない） | 別の ADR で扱う |
| `CONFIRM`（発信） | **起こせない（維持）** | 発信の直前の確認は、引き続きタッチの 1 か所だけ |

- 公開する面は、`VoiceSessionHooks` に `onVisitorNameConfirmed(name)` の 1 つを足すだけにする。
- `exposure-guard.test.ts` は、「公開するのは `onResolved` と `onVisitorNameConfirmed` だけ」「音声から dispatch するのは `SELECT_TARGET` と `SUBMIT_VISITOR_INFO` だけ」「`CONFIRM` は音声から dispatch しない」に改め、縛り続ける。
- `REQUIRES_CONFIRMATION_ACTIONS` の `submitVisitorInfo` は外さない。音声の経路では、「明示の操作」を**復唱への肯定**と定義する（下の 3）。

### 2. プライバシー通知をどこで、どう見せるか

- **氏名を聞き取るのは、`inputVisitorInfo` の画面に居るときだけ**にする。ほかの画面（目的の選択・相手の選択・idle）の発話から氏名を抜き出しても、その場では使わない。氏名を先回りで埋めるために、`inputVisitorInfo` の画面を飛ばすことはしない（#1088 の `materializationActionsForDraft` を、`inputVisitorInfo` で止まる形に直す）。
- `inputVisitorInfo` に入ったら、まず `PrivacyNotice` の要約を画面に表示する（#314 の現行どおり、入力欄より上）。氏名を尋ねる前に、TTS で通知の短い版を読み上げる。例:「受付のため、お名前をお伺いします。記録の扱いは画面に表示しています」。通知を読み上げ終わるまで、氏名の聞き取りを始めない。
- 通知の文面の正本は、`resolvePrivacyNoticeContent` のまま変えない。読み上げる短い版は、同じ module から取り出す（文面を二重に持たない）。
- 通知の要約は、タッチの経路と同じものを見せる（音声だけ別の文面にしない）。
- 公共空間で氏名を声に出させることへの配慮として、次を入れる。
  - 通知の中で、「声に出したくない場合は、画面から入力できる」ことを示す。
  - キーボードの入力欄は、常に同じ画面に置く（下の 4）。

### 3. 聞き違いへの対策

**a. STT の確信度の下限**
- 氏名の候補として扱うのは、STT の確信度が `minSttConfidence`（既定 0.6。`DEFAULT_ENTITY_RESOLUTION_THRESHOLDS`）以上で、**かつ**抽出器の確信度が高いときだけにする。
- 下限を下回ったら、候補として画面に出さずに、もう一度尋ねる。
- 目的（purpose）を音声から扱うようになったときも、同じ下限を課す（#1090 MAJOR-2）。

**b. 氏名は、確信度に関係なく必ず復唱して確かめる（自動確定しない）**
- 相手（`SELECT_TARGET`）は、高信頼なら自動で採用しうる。一方、氏名は来訪者本人の個人情報で、聞き違えたまま担当者へ伝わると取り返しにくい。そのため、高信頼でも自動では確定しない。
- 復唱は、画面の表示と読み上げの両方で行う。例:「〇〇様でよろしいですか」。
- 来訪者の答えは、次のどちらでもよい（音声とタッチの等価）。
  - 声で「はい」「いいえ」と答える。
  - 画面のボタンを押す。
- 「はい」のときだけ、`onVisitorNameConfirmed` を呼ぶ。

**c. 言い直しの上限**
- 「いいえ」と言われた場合や、下限を下回った場合は、もう一度尋ねる。
- これが **2 回**続いたら、音声での氏名の聞き取りをやめる。キーボードの入力欄へフォーカスを移し、「画面から入力してください」と案内する。有人支援（#1074）が使えるときは、その導線も示す。

**d. 発信前の確認**
- `confirming` の画面（`ConfirmView`）には、引き続き氏名を表示する。
- 戻る操作で `inputVisitorInfo` へ戻り、キーボードで直せる。
- 音声で確定した氏名も、タッチで入力した氏名と同じ確認を通る。

**e. 変更を必ず確かめる**
- 発話から取った氏名の文字列に、上限の長さを設ける。上限は `VisitorInfoForm` の入力欄と同じにし、超えたものは候補にしない（#1090 MINOR-4）。

**f. 同じ姓の担当者が 2 人以上いるときは、相手も必ず復唱する（owner の決定、2026-10-28）**
- 相手（`SELECT_TARGET`）は、高信頼なら自動で採用しうる（上の 1）。ただし、在席・不在のどちらかの辞書に**同じ姓の担当者が 2 人以上**いるときは、完全一致の人が 1 人だけでも自動で確定しない。必ず復唱するか、来訪者に選んでもらう。
- 表示名が姓だけの人（「田中」）がいる場合も同じにする。確信度の差（完全一致と前方一致）を理由に、自動で確定しない。
- 不在の人を名指しされたときも同じで、同じ姓の別人がいれば「不在です」と断定せず、復唱して確かめる。
- 姓は表示名から推定する。区切りがあれば先頭の語で、無ければ先頭 2 文字以上の一致で判定する。推定は復唱が増える側（安全側）に倒す。実装は `kiosk-bridge.ts` の `sharesSurname`（#1285）。

### 4. キーボードだけでも、受付を最後まで済ませられる経路を残す

- `inputVisitorInfo` のキーボード入力欄（`VisitorInfoForm`）は、音声が使えるかどうかに関係なく、**常に表示して使える**ようにしておく。音声は、この画面の上に**足す**入力手段であって、置き換えではない。
- マイクの権限の拒否、STT の障害、`sttEnabled: false`（既定）、騒音、の**どの場合でも**、キーボードだけで `SUBMIT_VISITOR_INFO` → `CONFIRM` まで進める。
- ConversationDraft の planner（#1088）は、音声も有人支援も使えないときに `blocked` を返さない。キーボードでの入力（`collect`）を返す（#1088 MAJOR-2）。
- #1057（自由入力の排除）でキーボードを外すのは、**有人支援（#1074）が本番に配線され、owner が別途承認してから**とする。それまでは、この ADR の「キーボードを残す」が優先する。

### 5. カスタム受付フローとの関係

- 音声で埋めるのは `name` だけにする。カスタムフロー（#100）が定める必須の欄（`text`/`textarea`/`select`/`checkbox`）は、画面で埋める。
- `onVisitorNameConfirmed` を受けたら、`KioskFlow` は氏名を入力欄に入れる。そのうえで、**必須の欄がすべて埋まっているときだけ** `SUBMIT_VISITOR_INFO` を dispatch する。まだ必須の欄が残っていれば、`inputVisitorInfo` に留まり、その欄の入力を案内する。
- 目的の選択に応じて選ばれたカスタムフロー（`selectedFlow`）は、音声の経路でも変えない（今回、目的は音声から扱わない）。

### 6. 個人情報の扱い

- 音声で取った氏名は、キーボードで入力した氏名と同じ扱いにする。
  - 監査ログ・experience metrics・アプリログに出さない（`.claude/rules/pii-secret-minimization.md`）。
  - 計測には、件数・回数・経過時間だけを使う。
- 途中の認識結果（interim）は、氏名の欄にも記録にも残さない。復唱に出すのは、確定した 1 つの候補だけにする。
- `RESET`、無操作でのリセット（#125）、キャンセル、受付の完了のときは、ConversationDraft と聞き取りの途中の状態を**必ず捨てる**。前の来訪者の氏名が、次の来訪者の画面に出ないようにする（#1088 の残存リスク）。
- 音声の生データは、端末の外に送らず、保存もしない（既存の規則のまま）。

## 代替案

1. **ADR 0007 のまま（音声で氏名を扱わない）**
   - 安全側は最も強い。ただし、#1077 と #1057 の目的（氏名をタイプさせない）に届かない。owner の判断で採らない。
2. **高信頼なら復唱せずに氏名を確定する（#1088 / #1090 の現行の実装）**
   - 来訪者の手数は最小になる。一方で、聞き違えた氏名が確認を経ずに入る。
   - さらに、中間の画面を飛ばすので、プライバシー通知を見ないまま氏名を取られる。
   - 取り返しにくい個人情報の確定には重すぎる危険なので、採らない。
3. **氏名の確定に加えて、`CONFIRM`（発信）も音声に開ける**
   - 「人を呼ぶ」という取り返しのつかない操作の手前の安全弁が、音声の認識と同じ経路に乗る。
   - ADR 0007 の「統合すると安全弁が弱まる」と同じ理由で、採らない。
4. **キーボードを先に外し、STT が使えないときは有人支援だけにする**
   - 有人支援（#1074）がまだ配線されていない。今キーボードを外すと、受付が行き止まりになる。採らない（上の 4）。

## 影響

### 実装（この ADR が承認されてから）
- **#1088**:
  - planner を `inputVisitorInfo` で止める。氏名は prefill の値として返す。
  - 音声も有人支援も使えないときは、`collect`（キーボード）を返す。
  - 無効な値が後から来た有効な値を阻まないように、`mergeSlot` を直す。
- **#1090**:
  - 氏名と目的に、STT の確信度の下限を課す。
  - 同じ姓の不在の人による誤接続を直し（#1284 と同じ型）、それを正解として縛っているテストを直す。
- **#1086**:
  - 文書を、この ADR に合わせる。対象は、ui-contract との食い違い、カスタムフロー、失敗時の導線、PII 表示の制約。
- **`KioskFlow` / `kiosk-binding`**:
  - `onVisitorNameConfirmed` を足す。復唱の UI と、言い直しの上限を入れる。
  - 通知を読み上げ終えてから聞き取りを始める。
  - `exposure-guard.test.ts` を、上の 1 のとおりに改める。

### 運用・コスト
- 新しい外部送信や依存は無い（STT は既存の経路）。
- 受付 1 件あたりの読み上げ（通知と復唱）が増えるので、所要時間が数秒延びる見込み。受付の完遂率と所要時間の計測で確かめる。

### 撤回の条件
次のどれかが起きたら、音声での氏名の確定を止め（`onVisitorNameConfirmed` を配線から外す）、ADR 0007 の境界へ戻す。
- 聞き違えた氏名が担当者へ伝わった事例が、運用で確認された。
- 復唱の往復で、受付の完遂率が下がった。

撤回しても、キーボードの経路が常に残っているので、受付は止まらない。

## owner の決定（2026-10-28）

- 提案のとおり承認する。
- 言い直しの上限は「2 回」とする。
- 通知の読み上げは、毎回の受付で行う（省略の設定を設けない）。
- 来訪の目的（`SELECT_PURPOSE`）は、音声で聞き取る対象に入れない（この ADR の範囲外）。
- 同じ姓の担当者が 2 人以上いるときは、相手も必ず復唱する（上の 3-f）。
