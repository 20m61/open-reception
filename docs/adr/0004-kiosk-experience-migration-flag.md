# ADR 0004: 新旧 KioskFlow の切替方式（移行フラグの粒度・解決順・撤去条件）

- ステータス: 承認（構成取得の切替まで実装済み。ExperienceShell 分割の切替も本方式に従う）。
- 関連: issue #422（本 ADR の対象）、#419（`EffectiveKioskConfiguration` / `ProductContext`）、
  #420（受付体験の版）、#418（親 Epic）
- 関連ドキュメント: `docs/product-integration-plan.md` §7 Feature flag registry・§9 Breaking-change
  register・§10 Rollback playbook
- 実装: `src/domain/kiosk/experience-flags.ts`、`src/components/kiosk/useEffectiveConfiguration.ts`、
  `src/components/kiosk/KioskFlow.tsx`

## 背景

`KioskFlow.tsx`（3196 行）を段階的に置き換える。移行台帳 §10 の原則は「ロールバックは
**フラグを戻すだけ**で完了できる形にする」で、そのためには新旧を同居させる切替点が要る。
台帳 §8 は「新旧 KioskFlow の切替方式（feature flag の粒度・撤去条件）」を ADR が要る決定として
挙げていた。

決めるべきは 3 点:

1. **粒度** — テナント機能フラグに載せるか、別立ての移行フラグにするか
2. **解決順** — どこから値を取り、何が優先するか
3. **撤去条件** — いつフラグと旧経路を消すか

## 決定

### 1. 粒度: テナント機能フラグとは**別立て**の「移行フラグ」にする

既存の `TENANT_FEATURE_FLAG_KEYS`（`voiceSynthesis` / `avatarReception`）に追加**しない**。
両者は寿命と意思決定者が違う:

| | テナント機能フラグ | 移行フラグ |
| --- | --- | --- |
| 問い | そのテナントがその機能を使うか | 新旧どちらの経路で動くか |
| 寿命 | 恒久 | 移行完了で**撤去** |
| 決める人 | テナント運用者（`/platform/feature-flags`） | 開発・移行の実施者 |

同居させると、撤去期限のある値が恒久フラグの管理面に紛れ、消し忘れが二重経路として residue に
なる。`src/domain/kiosk/experience-flags.ts` に `KioskExperienceFlags` として分離し、台帳 §7 の
registry には**撤去条件を必ず書く行としてのみ**登録する。

### 2. 解決順: ビルド時 env → URL クエリ（後勝ち）。**端末 1 台単位で切り戻せること**を要件にする

```
NEXT_PUBLIC_KIOSK_EFFECTIVE_CONFIG（環境ごとの既定）
  → ?effectiveConfig=1|0（端末単位の上書き・最優先）
```

**サーバ側の構成（`EffectiveKioskConfiguration.featureFlags`）に載せない。** 載せると、
「構成取得の経路を切り替えるフラグを、その構成取得で取る」という循環になり、新経路が壊れた
ときに切り戻せない。ロールバック手段は障害の影響を受けない場所に置く。

クエリ上書きは**本番でも塞がない**。`?debugScanPayload=`（予約トークンを URL に載せるため
本番では無効）と違い、このフラグは秘匿値を運ばず、既存のタイマー上書き（`?inactivityMs=`）と
同じ流儀に収まる。運用上の利点が大きい: 1 台だけ新経路で試す・不調な 1 台だけ戻す、が
デプロイなしでできる。

**既定は旧経路**（フラグ未指定 = false）。移行フラグは「明示的に入れる」まで倒れない。

### 3. 失敗時の挙動: 新経路が失敗した端末は**旧経路へ自動フォールバック**する

`/api/configuration/effective` は fail-closed（未エンロール端末・越境は 403、セクション取得
不能は 503）。これは配信側として正しいが、**端末側でそのまま無設定にすると受付が成立しない**。
そこで端末は取得失敗を検出したら旧個別 API を叩き直す。フォールバックは可用性のための
自動処置であって、恒久的な切り戻しは 2 の手段（フラグ）で明示的に行う。

この自動フォールバックが成立する前提は「旧経路が生きていること」なので、**台帳 §9 B-03
（個別設定 API の撤去）を実施した時点でこの安全網は消える**。だから B-03 の前に、フラグ既定を
新経路へ倒した状態での観測が要る（下記「撤去条件」）。

### 4. 切替の単位: 「構成取得」と「シェル分割」で**別のフラグにする**

1 つのフラグに束ねない。構成取得の切替（増分 1）は挙動が同じであることを機械的に検証できるが、
シェル分割は見た目・遷移が変わりうる。まとめると、VRT 差分が出たときに「取得経路が原因か
描画構造が原因か」を切り分けられず、片方だけ戻すこともできない。

- `effectiveConfiguration` … 構成取得の新旧（本増分で追加）
- （後続）ExperienceShell 切替 … 分割シェルの新旧

## 代替案

| 案 | 却下理由 |
| --- | --- |
| テナント機能フラグ（`TENANT_FEATURE_FLAG_KEYS`）に追加 | 寿命が違う値が混ざり、撤去期限が管理面から見えなくなる。テナント運用者に移行の可否を判断させることにもなる |
| `EffectiveKioskConfiguration.featureFlags` から読む | 循環依存。新経路が壊れたときに切り戻せない |
| env のみ（クエリ上書きなし） | 1 台だけ試す/戻すのに再デプロイが要る。台帳 §10 の「フラグを戻すだけ」を満たさない |
| フラグを持たず一度に切り替える | ロールバックが revert のみになる。台帳 §10 の原則に反する |
| 失敗時もフォールバックしない（fail-closed を端末まで貫く） | 端末が無設定で固まる。可用性維持（#419 の「拒否しない = 記録して続ける」方針）と整合しない |

## 影響（運用・撤回条件）

- **コスト影響なし**（クライアント分岐のみ。追加依存なし）。
- **セキュリティ境界を動かさない**。スコープ解決の権威は引き続きサーバ（セッション束縛）に
  あり、クライアントは tenant/site/kiosk を送らない。フラグが変えるのは「どの経路で取るか」だけ。
- **観測**: 新経路の 4xx/5xx とフォールバック発生は、フラグ既定を倒す判断の入力になる。

### 撤去条件

1. フラグ既定を新経路へ倒し、**全端末が新経路のみで構成を取れる**ことを 2 wave 観測する
   （未エンロール端末が 403 でフォールバックしていないこと）。
2. 台帳 §9 B-03（個別設定 API の撤去）を実施する。
3. **同時に**フラグ分岐・旧経路・`experience-flags.ts` の当該キーを削除する。旧経路が消えた後に
   フラグだけ残すと、倒しても戻り先が無い「効かないスイッチ」になる。
